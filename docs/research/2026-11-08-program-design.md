# Product judgment and program design before implementation

2026-11-08. Which choices should Flow surface before an agent writes code? These are candidate practices. The sources are two auto-captioned workshops and a published interview transcript. Their examples illustrate methods and do not measure their impact on Flow.

| Source and observed example | Implication for Flow |
| --- | --- |
| Kent C. Dodds has workshop participants interview people who waited outside. Questions about the last occurrence, the workaround and its cost elicit evidence that a pitch for preregistration cannot. He also describes customer interviews changing a software distribution decision because security fixes had to reach users promptly. [Part 1, 27:28](https://www.youtube.com/watch?v=_fHTqOs5wQA&t=1648s) · [Interview exercise, 39:21](https://www.youtube.com/watch?v=_fHTqOs5wQA&t=2361s) | When evidence is weak, ask for one actual incident and its consequence. Carry the consequence into the spec if it rules out an architecture. |
| Dodds works backward from facial recognition at workshop check-in to the attendee's job. Parallel queues become plausible, while face storage introduces ongoing obligations. Later he uses the Kano model to distinguish expected basics, improvements whose degree matters, and delighters. [Part 2, 9:53](https://www.youtube.com/watch?v=s0hFne6EeOI&t=593s) · [State, 18:47](https://www.youtube.com/watch?v=s0hFne6EeOI&t=1127s) · [Prioritization, 39:29](https://www.youtube.com/watch?v=s0hFne6EeOI&t=2369s) | Compare the state each plausible solution creates. When cutting scope, protect the minimum experience users take for granted and identify which improvement can wait. |
| Dex Horthy works through call paths, file ownership and type signatures in conversation, then builds a narrow path he can exercise while redirection is cheap. He qualifies the investment for exploratory startups. [Interview transcript](https://prepublish.ai/youtube-transcript/xgkjtF89-44) · [Timed walkthrough, 18:50](https://www.youtube.com/watch?v=xgkjtF89-44&t=1130s) | In a consequential case, show one operation crossing the disputed boundary, including the owner of writes and the observable failure. Try the sketch against a plausible second caller or change. |

## Fit with current skills

[Explore](../../skills/explore/SKILL.md) already covers workarounds, assumptions, experiments and outcomes. [To Spec](../../skills/to-spec/SKILL.md) already permits sketches for material uncertainty. [To Tasks](../../skills/to-tasks/SKILL.md) already requires demonstrable vertical slices. The missing guidance is a concrete way to recognize and expose a consequential choice. The starter can settle framework and repo conventions while leaving authority over a domain operation unresolved.

Candidate experiment for the next cross-boundary feature: add a short call path under Decisions, explain which alternative it rules out, and exercise it in the first slice. At review, record whether it exposed a disagreement early and whether the ownership choice needed rework. A local change following an established pattern is a comparison case where no sketch is warranted. A standalone program-design skill would introduce another invocation and handoff before there is evidence that the existing spec cannot carry this work.
